# حلقه کیفیت — هدف خطای زیر ۱٪

## چرا حلقه؟

گزارش اول ایجنت‌ها معمولاً ناقص است: منبع کم، ادعاهای کلی، تکرار کار قبلی، قاطی شدن واقعیت و فرض. یک بار «خواندن و حس خوب» کیفیت نیست.

## جریان

```text
[1] MGT ابلاغ
[2] ایجنت می‌خواند: JOB + ACTIVITY-LOG + COVERED + CURRENT
[3] ایجنت خودآزمایی با چک‌لیست واحد (self-check)
[4] تحویل به outbox
[5] QA رأی با روبریک
        ├─ fail-critical → برگشت فوری، بدون مذاکره
        ├─ fail          → برگشت با فهرست نقص
        └─ pass          → ثبت accepted + باز شدن راه تسک بعد
[6] اگر fail: برو به [3] با همان TASK-ID و revision+1
[7] اگر 3 بار fail شد: MGT دامنه را خرد می‌کند یا ایجنت را عوض می‌کند
```

## تعریف خطا

چک‌لیست هر تسک از دو لایه ساخته می‌شود:

| لایه | منبع | تحمل خطا |
| --- | --- | --- |
| بحرانی (C) | بندهای C در `RUBRIC.md` + بندهای اجباری بریف | **صفر** |
| عمده (M) | پوشش ابعاد اجباری، تناقض داخلی، تکرار کار قبلی | **صفر برای pass** |
| جزئی (m) | نثر، ترتیب، لینک شکسته غیرکلیدی | کمتر از ۱٪ اقلام جزئی |

فرمول قبول:

```text
C_fail = 0
M_fail = 0
m_fail / m_total < 0.01
```

اگر چک‌لیست جزئی ۱۰۰ بند دارد، حداکثر ۰ نقص جزئی برای رعایت سخت‌گیرانه زیر ۱٪ در عمل یعنی **تقریباً صفر**؛ برای تسک‌های کوچک (m_total < 100) حتی یک نقص جزئی هم بالای ۱٪ است و باید درست شود مگر `QA` آن را `nit` غیرمسدود ثبت کند و `MGT` بپذیرد.

در این سازمان پیش‌فرض سخت است: **nit هم باید قبل از pass بسته شود** مگر صریحاً `accepted-nit` در برگه رأی بیاید.

## خودآزمایی اجباری ایجنت مجری

قبل از outbox، ایجنت جدول زیر را ته گزارش پر می‌کند. خالی = رد خودکار.

| بند | بله/خیر |
| --- | --- |
| ACTIVITY-LOG را خواندم | |
| موضوع تکراری ننوشتم مگر ارجاع | |
| هر ادعای غیر بدیهی منبع دارد | |
| فرض‌ها برچسب `فرض` دارند | |
| همه ابعاد اجباری بریف پر است | |
| خارج از دامنه نرفته‌ام | |
| مسیر فایل همان بریف است | |

## ضدتقلب کیفیت

- کپی از ویکی/بلاگ بدون تحلیل بومی = نقص عمده
- فهرست بدون مشاهده صفحه واقعی = نقص بحرانی برای تسک کالبدشکافی سایت
- «به نظر می‌رسد حرفه‌ای است» بدون شاهد = نقص عمده
- رنگ/فونت/دسته بدون ثبت مشخص = نقص عمده در تسک UI

## متریک واحد QA

در `ACTIVITY-LOG` هفتگی:

- تعداد تسک بررسی‌شده
- میانگین revision تا pass
- پرتکرارترین کد نقص
- واحدهایی که بیش از یک بار در C شکست خورده‌اند
