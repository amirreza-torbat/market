## 1. خلاصه اجرایی

قالب `D00..D73` روی HKTDC Sourcing در حالت مهمان اجرا شد. هر **74/74 بُعد** دقیقاً یک ردیف دارد و validator برای هر ردیف یا `observed` یا `observed-not-found`، URL کامل HTTPS، تاریخ مشاهده، نوع شاهد، access mode و confidence را الزام می‌کند [D1][D2]. نتیجه اعتبارسنجی ماشینی: **74 ردیف، 74 شناسه یکتا و صفر خطای schema**؛ واحد شمارش «بُعد قالب» و تاریخ برش 2026-08-24 است [D1][D2]. اطمینان: **بالا**.

از 74 بُعد، **55 مورد observed** و **19 مورد observed-not-found** شد. این دو عدد به‌ترتیب 74.3٪ و 25.7٪ ماتریس‌اند (`55÷74×100` و `19÷74×100`، گردکردن فقط در نمایش) [D1][D2]. «مشاهده نشد» به معنی نبود قابلیت نیست؛ فقط یعنی در صفحات عمومی/راهنمای رسمی بررسی‌شده و بدون حساب یا تراکنش، شاهد کافی دیده نشد.

**نتیجه اعتبارسنجی:** schema پیشنهادی قابل استفاده است مشروط به اینکه:

1. evidence state از confidence جدا بماند؛
2. برای not-found، علت و روش بعدی اجباری باشد؛
3. واقعیت، استنباط و implication در ستون‌های جدا ثبت شوند؛
4. عدد بدون metadata کامل رد شود؛
5. actor/input/output/state/exception/dependency برای workflowها حفظ شود؛
6. مستقیم‌دیدن UI، راهنمای رسمی، policy و ادعای ناشر نوع شاهد متفاوت داشته باشند.

این تسک **تحلیل عمیق Alibaba یا RND-003 نیست**؛ HKTDC فقط fixture واقعی برای اعتبارسنجی قالب بود.

### 1.1 اصلاح QA با شناسه `m-DIM`

QA-002 نبود block صریح module/state را به‌عنوان observation ساختاری ثبت کرد. برای رفع دقیق آن، قالب اجرایی [`SITE-DOSSIER.md`](../templates/SITE-DOSSIER.md) با نسخه `RND-D00-D73-v1.1` ایجاد شد [T1]. زیر **هر یک از 74 بخش D00 تا D73** یک `Capability/Section Record` مستقل وجود دارد که این 12 فیلد را الزام می‌کند:

`actor`، `input`، `output`، `page/module`، `entity`، `event`، `state`، `error/exception`، `document`، `personal data`، `risk` و `handoff`.

این block فقط در مقدمه تعریف نشده است: کنترل ساختاری این اصلاح با شمارش مستقیم template تأیید می‌کند که 74 section و 74 block starter وجود دارد و هر block تمام 12 label را دارد [T1]. دستور داخل هر D نیز می‌گوید برای هر قابلیت/بخش اضافی، کل Capability Record و Evidence Record جداگانه تکرار شود؛ بنابراین یک توضیح کلی نمی‌تواند جای module/state سطح قابلیت را بگیرد. فایل‌های داده `RND-002` تغییر نکردند، چون observation درباره artifact قالب بود، نه شواهد fixture.

## 3. تعریف schema اعتبارسنجی‌شده

### 3.1 هویت و سؤال

`dimension_id`, `group`, `field_name`, `question`

### 3.2 شاهد

`evidence_state`, `observed_fact`, `evidence_url`, `evidence_type`, `observed_at`, `region`, `access_mode`, `confidence`

- `observed`: شاهد مثبت در UI عمومی یا سند رسمی.
- `observed-not-found`: شاهد مثبت کافی پیدا نشد؛ نیازمند علت و روش بعدی.
- confidence فقط کیفیت/مستقیم‌بودن شاهد را می‌سنجد و جای evidence state نیست.

### 3.3 workflow

`actor`, `input`, `output`, `system_state`, `exception_path`, `cost_time`, `risk`, `dependency`

### 3.4 تحلیل

`inference`, `gap_reason`, `next_method`, `product_implication`

### 3.5 metadata عدد

`metric_name`, `metric_value`, `metric_unit`, `metric_currency`, `metric_period`, `metric_territory`, `metric_classification`, `metric_method`, `metric_publisher`, `source_title`, `source_publication_date`

برای موارد غیرمالی، currency=`not applicable`؛ برای این تسک HS/classification=`not applicable` یا taxonomy متناظر است. عدد مفقود صفر تلقی نمی‌شود.

## 8. یافته‌های شماره‌دار

### F1 — not-found باید یک نتیجه معتبر و ساخت‌یافته باشد

**واقعیت:** 19 بُعد not-found است و همه gap reason، next method و URL محل بررسی دارند [D1]. موارد شامل sort، role selector، mandatory KYB documents، sample state، PO/PI، escrow، Incoterms، trade docs، tracking، inspection transaction، delivery confirmation، buyer verification، reviews، fraud-report action، SLA، mobile، accessibility و performance است.
**استنباط:** سلول خالی ambiguity ایجاد می‌کند؛ not-found ساخت‌یافته کیفیت handoff را بالا می‌برد.
**پیشنهاد:** validator این سه فیلد را برای not-found اجباری نگه دارد.
**اطمینان:** بالا.

### F2 — evidence type باید از confidence جدا باشد

**واقعیت:** 53 ردیف confidence بالا و 21 ردیف متوسط است؛ confidence پایین وجود ندارد [D1]. بعضی یافته‌ها مستقیم از UI، بعضی از official support/policy و برخی از supplier-entered listing آمده‌اند.
**استنباط:** «رسمی» الزاماً «مشاهده مستقیم workflow» نیست و supplier-entered content نیز تضمین پلتفرم نیست.
**پیشنهاد:** `evidence_type` و `confidence` هر دو حفظ شوند.
**اطمینان:** بالا.

### F3 — transaction به state و exception نیاز دارد

**واقعیت:** checkout در نبود shipping option متوقف می‌شود تا supplier fee بدهد؛ order support پنج payment/order state مشخص دارد [S09][S10].
**استنباط:** feature checklist بدون state/exception، مسیر واقعی را ناقص می‌کند.
**پیشنهاد:** actor/input/output/system_state/exception_path در schema اجباری مشروط شوند.
**اطمینان:** بالا.

### F4 — verification، inspection و escrow مترادف نیستند

**واقعیت:** HKTDC certificate-label verification را با third parties مستند می‌کند [S14]؛ اما order-linked inspection یا HKTDC escrow در منابع scoped مشاهده نشد. dispute پرداخت به PayPal ارجاع می‌شود [S16].
**استنباط:** ادغام این مفاهیم یک false positive بحرانی می‌سازد.
**پیشنهاد:** verification scope، shipment inspection، payment processor protection و escrow چهار فیلد مستقل باشند.
**اطمینان:** بالا.

### F5 — policy و UX باید همزمان اما جدا ثبت شوند

**واقعیت:** Terms رفتارهای ممنوع و automation ban را بیان می‌کند، Privacy داده‌ها/کاربردها را توضیح می‌دهد، ولی suspension/appeal workflow و in-context fraud report مشاهده نشد [S11][S18][D1].
**استنباط:** وجود policy اثبات وجود control یا UX اجرایی نیست.
**پیشنهاد:** policy_rule، control، user_action و appeal_state جدا بمانند.
**اطمینان:** بالا.

### F6 — قیمت/عدد بدون زمینه قابل مقایسه نیست

**واقعیت:** هشت claim عددی در matrix دارای نام شاخص، مقدار، واحد، ارز، دوره/territory، classification، روش، ناشر، عنوان و تاریخ انتشار هستند [D1][D2].
**استنباط:** یک ستون value به‌تنهایی برای قیمت، زمان، تعداد حالت یا frequency کافی نیست.
**پیشنهاد:** numeric metadata فعلی حفظ و نبود فیلد باعث fail validator شود.
**اطمینان:** بالا.
