## کنترل repository و branch

پیش از هر ویرایش:

```bash
git remote get-url origin
git branch --show-current
git status --short --branch
git log -1 --oneline
```

`origin` باید `https://github.com/amirreza-torbat/market.git` باشد. اگر repository یا branch نشست مشخص نیست، حدس نزن، فایل نساز و متوقف شو. شاخه RND فقط read-only است؛ آن را checkout یا ویرایش نکن.

## پیش‌شرط

وجود `QA-PASS-RND-001` را از remote قابل تأیید کن. اگر وجود ندارد، رأی `C-PATH` بده و RND-002 را داوری نکن.

## منبع مورد داوری

شاخه و commit واقعی RND را از ابلاغ `MGT` یا remote تشخیص بده؛ از نام شاخه حدس نزن. مسیرهای مورد انتظار:

```text
docs/units/RND/outbox/RND-002.md
docs/units/RND/outbox/RND-002/
docs/units/RND/packages/RND-002-to-<UNIT>.md
docs/units/MGT/inbox/NOTIFY-RND-002.md
```

فقط فایل‌هایی را داوری کن که در commit/branch واقعی RND وجود دارند. برای خواندن بدون checkout:

```bash
git fetch origin <RND_BRANCH>
git show origin/<RND_BRANCH>:docs/units/RND/outbox/RND-002.md
```

اگر گزارش یا فایل‌های اجباری در remote قابل دریافت نیستند، `C-PATH` یا `C-SOURCE` ثبت کن و متوقف شو.

## هدف QA-002

بررسی کن آیا قالب تحلیل عمیق برای اجرای RND-003 آماده و قابل تکرار شده است؛ نه اینکه Alibaba یا سایت دیگری را به‌صورت کامل تحلیل کنی.

## چک‌لیست اجباری

### ۱. دامنه و هدف

- آیا فقط اعتبارسنجی قالب انجام شده است؟
- آیا RND-003 یا تحلیل کامل سایت شروع نشده است؟
- آیا out-of-scope روشن است؟

### ۲. پوشش قالب D00 تا D73

- آیا همه ابعاد `D00` تا `D73` وجود دارند؟
- آیا هیچ بعدی فقط عنوان خالی نیست؟
- آیا برای هر بعد فیلدهای واقعیت، شاهد، استنباط، implication و مشاهده‌نشدن وجود دارد؟
- آیا قالب برای مقایسه بین سایت‌ها یکنواخت است؟

### ۳. شواهد و منابع

- آیا برای هر ادعا URL، تاریخ دسترسی و confidence وجود دارد؟
- آیا مشاهده مستقیم از استنباط جدا شده است؟
- آیا منابع رسمی، صفحه، screenshot/reference و query log پیش‌بینی شده‌اند؟
- آیا نبود داده با «مشاهده نشد + علت + روش بعدی» ثبت می‌شود؟

### ۴. سفر فروشنده

بررسی کن قالب همه این مراحل را پوشش می‌دهد:

ثبت‌نام، احراز، پروفایل شرکت، ظرفیت، ساخت کالا، مشخصات، HS، استاندارد، قیمت، MOQ، Incoterms، انتشار، moderation، RFQ، پیشنهاد، نمونه، مذاکره، سفارش، پرداخت، بازرسی، اسناد، حمل، تحویل، تسویه، امتیاز و اختلاف.

### ۵. سفر خریدار

بررسی کن قالب همه این مراحل را پوشش می‌دهد:

ورود، جست‌وجو، فیلتر، مقایسه، احراز خریدار، RFQ، دریافت پیشنهاد، چت، نمونه، PO، قرارداد، پرداخت، escrow/LC، بازرسی، بیمه، حمل، رهگیری، تحویل، claim، اختلاف، امتیاز و سفارش تکراری.

### ۶. ماژول و state

آیا قالب برای هر قابلیت این موارد را ثبت می‌کند؟

```text
actor
input
output

```

### ۷. کیفیت نمونه اجرا

اگر RND قالب را روی سایت نمونه اجرا کرده است، بررسی کن:

- نمونه واقعاً قابل بازتولید است؛
- حداقل ۳ واقعیت قابل راستی‌آزمایی برای هر بخش مهم وجود دارد؛
- موارد مشاهده‌نشده جعل نشده‌اند؛
- قالب در عمل قابل استفاده است، نه فقط روی کاغذ؛
- نتیجه نمونه با schema قالب سازگار است.

### ۸. خروجی برای واحدهای بعدی

بررسی کن handoff مشخصی برای `PM`, `DES`, `FIN`, `TRADE`, `TNS` و `MGT` وجود دارد و هر handoff شامل implication، dependency، risk و next action است.

### ۹. تکرارپذیری و QA

- آیا گزارش با همان ورودی دوباره قابل تولید است؟
- آیا self-check نویسنده وجود دارد؟
- آیا محدودیت‌ها و open questions ثبت شده‌اند؟
- آیا قالب برای RND-003 دستورالعمل روشن دارد؟

## رأی

طبق rubric:

- هر ادعای بدون منبع کلیدی: `C-SOURCE`؛
- نبود ابعاد اجباری یا سطحی‌بودن آن‌ها: `M-DIM`؛
- خروج از دامنه و شروع RND-003: `C-SCOPE`؛
- مسیر اشتباه یا منبع غیرقابل دریافت: `C-PATH`؛
- handoff ناقص: `M-HAND`؛
- مجهولات ثبت‌نشده: `M-NEXT`؛
- نقص جزئی فقط در صورت کمتر از ۱٪ اقلام قابل‌شمارش مجاز است.
